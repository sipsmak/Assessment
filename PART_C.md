# Part C - Production approach on GCP / BigQuery

For production, I would land each source batch unchanged in a date-partitioned Cloud Storage raw zone and load it into a BigQuery staging table with ingestion metadata such as `batch_id`, `source_file`, `ingestion_ts` and a row hash. I would validate and standardise the batch in staging, then use a BigQuery `MERGE` into the current-state bookings table on `booking_id`. The update branch would only execute when the incoming `updated_at` is newer; equal timestamps with different row hashes would be quarantined and alerted rather than silently overwriting. The reporting fact would be partitioned by `check_in` month and clustered by `property_id`, `booking_channel` and `booking_status`. Queries and transformations would always filter partition columns, select only required fields, process only affected partitions, and use incremental `MERGE` statements rather than rebuilding the full table. For tens of millions of rows I would also monitor bytes scanned, slot usage and partition sizes.

I would orchestrate the flow with Cloud Composer (Airflow) or, for a smaller workload, Cloud Scheduler triggering a Cloud Run job. The DAG would be: land -> validate -> stage -> merge -> enrich -> publish -> DQ checks. Cloud Logging and Cloud Monitoring would capture task failures, duration, row counts, reject rates and freshness. Data-quality checks would have agreed thresholds; critical failures such as duplicate current keys, missing FX coverage or unexpected reject-rate spikes would block publication and alert the team before dashboards refresh.

Code, SQL and infrastructure would live in Git with pull requests and protected main branches. CI would run `pytest`, SQL linting/validation and small integration tests using representative fixtures. CD would promote versioned artefacts through dev/test/prod with environment-specific configuration and service accounts. I would maintain a README, runbook/SOP for failures and backfills, data dictionary, ownership information and lineage (for example Dataplex/Data Catalog plus orchestration metadata) so changes can be traced from source batch to reporting view.

Given the assessment time limit, this submission uses CSV outputs and pandas to demonstrate the logic locally rather than deploying infrastructure. I assume `updated_at` is the source-of-truth version timestamp; exact re-sends are harmless; conflicting rows at the same latest timestamp are not safely resolvable and are quarantined; FX is based on `created_at` as specified; and only confirmed bookings count as recognised reporting revenue while pending and cancelled bookings remain in the analysis-ready current-state table for auditability. With more time I would add schema contracts, stronger reconciliation against source control totals, property-capacity-aware guest validation, integration tests in BigQuery and infrastructure-as-code. AI was used to help write the SQL and Python code after I had defined the intended logic and business rules. I then reviewed the generated code, ran the pipeline and tests, and adjusted the implementation where necessary before finalising the submission.
